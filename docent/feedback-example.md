## 2026-01-15

- **Disagreement** (on `policies/provenance.md`) - CORRECTION to the earlier Disagreement recorded against this concept on 2026-01-15 about actions/attest versus actions/attest-build-provenance. That entry asked whether build.yml's provenance attestation carries the `https://slsa.dev/provenance/v1` predicate the verifier in gate.yml requires. It does. Verified against the actions/attest release the workflow pins: its README documents three modes, and the Provenance mode applies when neither sbom-path nor any predicate input is supplied, in which case the action generates SLSA build provenance. build.yml's 'Attest' step supplies only subject-path, so it is in that default mode and is functionally equivalent to actions/attest-build-provenance. There is no predicate mismatch and no supply-chain gap here. What remains, and it is minor, is that the concept names actions/attest-build-provenance as the mechanism while the image build uses actions/attest in its default provenance mode; the outcome is the same, so this is wording to tighten rather than a defect to fix. Please disregard the risk framing in the earlier entry. - docent, for human:ada-lovelace

- **Disagreement** (on `platform/registries.md`) - The concept says build.yml checks every FROM line of a Dockerfile against the approved registries. That overstates the control. The 'Find registries' step only emits a registry when the FROM line already names a host under `registry.example.com`, and the 'Check registries' step iterates only over what that step found. A FROM line naming any other host is therefore never checked: tested on origin/main's logic, 'FROM alpine' and 'FROM docker.io/library/alpine' both produce zero registries, so the check never runs and both pass. The effective rule is 'among the organization's own registries, only approved ones', not 'only approved registries'. Suggest the concept state the detection scope, since a reader may otherwise take the list for a complete base-image control. - docent, for human:ada-lovelace

- **Disagreement** (on `policies/provenance.md`) - The concept says every build 'generates a build provenance attestation with actions/attest-build-provenance'. That holds for the other builds, but not for the image build: on origin/main, build.yml step 'Attest' uses actions/attest with only subject-path, with no predicate-type or predicate supplied. This matters beyond wording, because gate.yml verifies that attestation with 'gh attestation verify --predicate-type `https://slsa.dev/provenance/v1`', which is the predicate actions/attest-build-provenance emits. Whether the image build's attestation carries that predicate type needs confirming at the source, and nothing in this repository exercises it, so a consumer repository would be first to hit any mismatch. Suggest the concept distinguish the image build from the rest, and that the curator confirm which action it is meant to use. - docent, for human:ada-lovelace

Worth a concept because the review playbook makes metadata keys part of the public contract a reviewer must hold steady, so a reviewer needs a baseline of the key names to detect a rename; also because the label set differs between image types, and that is not recorded anywhere in the bundle. - docent, for human:ada-lovelace
